1. INTRODUCTION
----------------------------------------------------------------

Test Plan Approach/Objective:

  The objective of this test plan is to verify that the Checkers
  game application behaves correctly according to the standard
  rules of Checkers/Draughts. Testing will confirm that piece
  movement, jump/capture logic, king promotion, turn enforcement,
  and win/loss detection all function as intended across both the
  GUI (Swing) and text-based console game modes.

  The approach combines black-box testing — interacting with the
  game as a user and observing behavior — with white-box testing
  that targets individual methods directly to cover edge cases not
  easily reached through normal play.

----------------------------------------------------------------
2. SCOPE
----------------------------------------------------------------

Features to be Tested:
  - Board initialization for both 8x8 and 10x10 board sizes
  - Correct starting piece placement for both players
  - Turn alternation (Black moves first; turns alternate correctly)
  - Normal piece movement (diagonal forward, one step only)
  - Rejection of invalid moves (backward, non-diagonal, white tiles)
  - Jump/capture movement (2 diagonal steps over an enemy piece)
  - Mandatory jump enforcement (player must jump if one is available)
  - Multi-jump chaining (same piece must continue if further jumps exist)
  - Piece removal from board after being captured
  - King promotion (piece reaching the opposite end becomes a King)
  - King movement (Kings move diagonally forward and backward)
  - King jump/capture in all four diagonal directions
  - Win condition (opponent has no pieces remaining)
  - Resign option (current player concedes the game)
  - Help menu displaying correct game rules

Features NOT to be Tested (and Why):
  - Network/multiplayer — not implemented; outside project scope
  - AI opponent — not implemented; outside project scope
  - Undo/redo of moves — not implemented; outside project scope
  - Draw or stalemate detection — not required by project specification
  - Pixel-level GUI rendering accuracy — subjective and
    environment-dependent; verified informally by visual inspection
  - Performance or stress testing — a two-player board game has no
    meaningful performance threshold to measure against

----------------------------------------------------------------
3. TESTING STRATEGY
----------------------------------------------------------------

Testing Types Used:

  Black-Box Testing:
    The game is played end-to-end by testers who interact only
    through the GUI or console interface. Test cases are derived
    entirely from the rules of Checkers, with no knowledge of the
    internal code structure. Testers attempt both legal and illegal
    actions and verify that the game responds correctly in each case.

    Example scenarios:
      - Clicking an empty destination before selecting a piece
      - Attempting to move a piece backward (normal piece)
      - Attempting to move onto a white (non-playable) tile
      - Attempting to skip a mandatory jump and make a normal move
      - Performing a valid jump and verifying the captured piece is removed
      - Moving a piece to the opposite end and verifying King promotion
      - Chaining multiple jumps with the same piece in one turn

  White-Box Testing:
    Internal logic is examined directly by inspecting method behavior
    with known inputs and verifying outputs. Branches and edge cases
    within Board, Pieces, and Player are targeted, including conditions
    that are difficult to trigger through normal gameplay.

    Methods and logic targeted:
      - Pieces.crowned()        — correct type change to KING variant
      - Pieces.moved()          — coordinate update after a move
      - Pieces.getType/getSide  — correct type and side reporting
      - Player.pieceEaten()     — piece count decrement and loss trigger
      - Player.lost()           — piece count set to zero on resignation
      - Board.jumpAvailable()   — correct detection of jumps in all
                                  directions, including Kings
      - Board.checkJump()       — validation of jump distance, enemy
                                  presence, and empty destination tile
      - Board.checkingTheCrown()— promotion triggered at correct rows

Test Levels Used:

  Unit Level:
    Individual classes (Pieces, Player) and isolated logic methods
    within Board are examined one at a time to confirm each behaves
    correctly in isolation.

  Subsystem Level:
    The full jump sequence is tested as a connected flow:
    jumpAvailable → checkJump → jumpPieces → pieceEaten → checkWin.
    This ensures that all the components of a capture work together
    correctly end-to-end.

  System Level:
    Complete games are played in both GUI mode and text-based console
    mode. Testers follow scripted scenarios from the opening move
    through to a win or resign screen, verifying overall behavior at
    the application level.

Test Summary Report:

  The following bugs were identified and resolved during development
  testing. A formal JUnit report will be appended once the unit test
  suite is executed.

  Bug 1 – King movement accepted straight-line moves
    King diagonal check used OR instead of AND, allowing moves that
    changed only one of row or column. Fixed by requiring both
    row distance and column distance equal 1. (~30 min)

  Bug 2 – Wrong piece captured during a jump
    The captured piece was retrieved before checkJump() had set the
    prey coordinates, so the wrong tile was read. Fixed by moving
    prey retrieval to after checkJump() completes. (~1 hour)

  Bug 3 – "Ghost piece" forcing invalid jumps
    checkJump() did not require exactly 2 diagonal steps, so clicking
    4 steps away produced a prey coordinate 2 tiles from the source
    rather than 1, hitting a real piece by coincidence. Fixed by
    adding a strict distance check. (~45 min)

  Bug 4 – "Not a valid jump distance" on legitimate moves
    movePieces() used shared mutable fields (currentRow/currentCol)
    for distance calculations instead of the piece's own position,
    causing desync after multi-jumps or stale turns. Fixed by using
    root.getRow()/getCol() as the authoritative source. (~2 hours)

  Bug 5 – Piece forced to jump over teammate
    jumpAvailable() did not verify the intermediate piece was an
    enemy, so a piece could be flagged as required to jump over its
    own teammate. Fixed by adding a side comparison check. (~30 min)

  Bug 6 – Player lost their turn on a bad click
    checkJump() called switchTurns() on failure, penalizing the
    player for clicking an invalid destination tile. Fixed by
    removing switchTurns() from checkJump(). (~15 min)
